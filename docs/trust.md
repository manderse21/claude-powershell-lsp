# Why trust this release

A first-time evaluator asking "why should I trust this?" usually has to reconstruct
the answer from scattered files. This page assembles the chain in one place. Every
link below points at a file in this repository or an artifact on the GitHub Release --
nothing here is asserted that the tree cannot support. Where a security team needs the
approve-or-deny detail (allow-listing, what runs locally, governance), that lives in
[TRUST.md](../TRUST.md); this page is the shorter, evaluator-facing map of the
verifiable evidence.

## The chain, link by link

### 1. Every release tag is signed -- keyless, no stored key

Each tag the release pipeline cuts is a **keyless gitsign (Sigstore) signature**: the
GitHub Actions runner authenticates with its ambient OIDC identity, Fulcio issues a
short-lived certificate, and the signature is logged in the public Rekor transparency
log. There is no long-lived key and no stored secret. The posture, the exact
`gitsign verify` invocation, and what a pass proves are in
[TRUST.md, "Signing posture"](../TRUST.md#signing-posture) and
[docs/RELEASING.md, "Verifying a release"](RELEASING.md#verifying-a-release).

### 2. Both release assets carry SLSA build provenance

Every tagged release publishes a source archive (`.tar.gz`, a `git archive` of the
exact tagged tree) and a CycloneDX SBOM (`.cdx.json`), and a single SLSA v1.0
build-provenance attestation covers both. Anyone can verify the archive against the
attestation with GitHub's own tooling:

```powershell
gh attestation verify powershell-lsp-1.17.0.tar.gz --repo manderse21/claude-powershell-lsp
```

The full step-by-step, with sample output and what the check proves, is in
[SECURITY.md, "Verifying release integrity"](../SECURITY.md#verifying-release-integrity)
and [docs/RELEASING.md, "Verifying a release"](RELEASING.md#verifying-a-release).

### 3. A CycloneDX SBOM, generated from the real pins

The SBOM (`powershell-lsp-1.17.0.cdx.json`, CycloneDX 1.5) lists the plugin and both
pinned downloaded dependencies. It is generated by
[`release/New-PluginSbom.ps1`](../release/New-PluginSbom.ps1), which reads the
dependency versions straight from the `ensure-*` scripts, so the SBOM cannot disagree
with what the tool actually downloads. See
[TRUST.md, "Supply-chain artifacts"](../TRUST.md#supply-chain-artifacts-sbom--build-provenance).

### 4. The analyzer is pinned AND hash-verified before use

The two components the plugin downloads on first run are each pinned to an exact
version and verified against a SHA-256 computed from the real known-good artifact
before they are used; a mismatch fails closed. The pinned PSScriptAnalyzer version and
its SHA-256 are tabulated in [TRUST.md, "What it downloads"](../TRUST.md#what-it-downloads-pinned-versions-and-pinned-hashes);
the pins themselves live in [`scripts/ensure-pssa.ps1`](../scripts/ensure-pssa.ps1) and
[`scripts/ensure-pses.ps1`](../scripts/ensure-pses.ps1), enforced by `Test-PinnedFileHash`
in [`scripts/lib/lsp-common.ps1`](../scripts/lib/lsp-common.ps1). Confirm a downloaded
component matches the pin this repo ships:

```powershell
(Get-FileHash -Algorithm SHA256 -LiteralPath .\PowerShellEditorServices.zip).Hash
```

### 5. Detections are held to a measured 0% false-positive bar

New detections are not shipped on judgement alone: each is measured against a
tool-derived known-good / known-bad oracle and held to a **0% false-positive rate and
100% true-positive coverage**, which is the evidence bar the project set for a new
detection (dispatches 000091 / 000092 / 000125). The measurement is not a one-time
claim -- it is recomputed from the live findings and mechanically guarded on every CI
run by [`tests/PowerShellLsp.Corpus.Tests.ps1`](../tests/PowerShellLsp.Corpus.Tests.ps1),
which also floors the sample size so the rate cannot be made defensible by shrinking the
oracle. The per-detection measurements are recorded, dispatch by dispatch, in the
[CHANGELOG](../CHANGELOG.md), and the corpus itself is described under
[README, "Diagnostic-correctness corpus"](../README.md#diagnostic-correctness-corpus).

### 6. Latency is measured, not asserted

The per-edit round-trip and the closed-loop re-check turn are measured, with method,
host, and sample size stated, in [docs/benchmarks.md](benchmarks.md) (measured
2026-07-17; warm-hook median 2228 ms over 30 iterations, cold start excluded). The page
is deliberately indicative and not a CI gate; the guarded thresholds live separately in
`tests/PowerShellLsp.Benchmark.Tests.ps1`.

### 7. The plugin scans its own product code

The plugin runs its own diagnostics over `scripts/` and uploads the result to GitHub
code scanning as SARIF, via
[`.github/workflows/powershell-lsp-code-scanning.yml`](../.github/workflows/powershell-lsp-code-scanning.yml).
That workflow's highest-privilege action -- the SARIF upload -- is pinned by full commit
SHA (`github/codeql-action/upload-sarif@7188fc363630916deb702c7fdcf4e481b751f97a`), not a
movable tag.

### 8. Every finding carries a generated rationale

Each surfaced finding carries a "why" that is generated from the pinned analyzer's own
metadata rather than asserted, regenerable under `-Check` from
[`scripts/regen-rule-rationales.ps1`](../scripts/regen-rule-rationales.ps1) into
[`rulesets/rule-rationales.psd1`](../rulesets/rule-rationales.psd1). The roadmap frames
this as a rule-rationale audit surface
([ROADMAP-powershell-lsp.md, E2.5](../ROADMAP-powershell-lsp.md)).

## What this page does not claim

The scripts are deliberately **not** Authenticode-signed, and the project has **not**
had a third-party security audit. Both limits are stated plainly in
[TRUST.md, "Honest limits"](../TRUST.md#honest-limits). This page assembles evidence that
already exists; it introduces no new claim, no code, and no version change.
